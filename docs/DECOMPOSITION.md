# Декомпозиция: AI-система ботов на базе Telegram

## Обзор системы

Платформа для клиентов: регистрация ботов (AI-агент + RAG + Telegram API), загрузка базы знаний, кастомизация, мониторинг. Доступ по подписке с пробным периодом 5 дней.

**Ключевые принципы:**
- **Интерфейс на естественном языке:** всё взаимодействие с системой — через диалог. Пользователь общается с агентом-помощником, который создаёт и настраивает RAG-ботов под нужды клиента.
- **Изоляция по контейнерам:** для каждого бота (клиента) создаётся отдельный контейнер; боты разных пользователей полностью независимы друг от друга.
- **Стек:** агенты (продукт + клиентские боты) — LangChain + LangGraph; RAG — Qdrant; LLM — GigaChat, YandexGPT (базово), поддержка других провайдеров.

**Два уровня агентов:**
- **Агент-помощник продукта** — один на платформу; пользователь общается с ним в Telegram (или веб-чате); помогает регистрировать ботов, загружать документы, менять промпты, запрашивать отчёты.
- **Клиентские RAG-агенты** — по одному на каждого бота; работают внутри своего контейнера; общаются с конечными пользователями клиента через Telegram-бота клиента.

### 0.3 Детализация: структура LangGraph агента-помощника

| Нода | Назначение | Входы | Выходы |
|------|------------|-------|--------|
| `router` | Определение intent по сообщению пользователя + контексту сессии | user_message, session_context | intent, extracted_params |
| `register_bot` | Вызов tool регистрации бота; уточняющие вопросы при необходимости | intent=register_bot, token (если есть) | tool_result, follow_up |
| `upload_document` | Вызов tool загрузки документа; запрос файла, если не приложен | intent=upload_doc, bot_id, file | tool_result |
| `update_prompt` | Вызов tool смены промпта; извлечение промпта из формулировки пользователя | intent=update_prompt, bot_id, user_formulation | tool_result |
| `get_report` | Вызов tool отчёта; уточнение периода при необходимости | intent=report, bot_id, period | tool_result |

**Intent-ы:** `register_bot`, `upload_document`, `update_prompt`, `get_report`, `list_bots`, `open_dashboard`, `start_trial`, `chitchat` (общие вопросы).

**Граф:** `router` → ветвление по intent → соответствующая нода → `respond` → END.

### 1.3 Детализация: оркестратор контейнеров

**Задачи оркестратора:**
- Создание контейнера при активации бота.
- Остановка/удаление при деактивации или удалении бота.
- Передача конфигурации в контейнер (token, config, env).

**Жизненный цикл контейнера:**

| Этап | Действие |
|------|----------|
| 1. Create | `docker run` (или K8s Job/Pod) с image `instant-chat-agent-bot` |
| 2. Config | Передать env: `BOT_TOKEN`, `BOT_ID`, `QDRANT_URL`, `CONFIG_SOURCE` (URL или путь) |
| 3. Run | Контейнер запускает long polling или регистрирует webhook |
| 4. Stop | При suspend/delete — `docker stop` / `kubectl delete` |

**Изоляция:**
- Сеть: контейнеры в отдельной bridge-сети; доступ только к Qdrant, LLM API, Telegram API.
- Ресурсы: `--memory`, `--cpus` (Docker) или limits в K8s.
- Данные: volume только для временных файлов; постоянные данные — в БД/Qdrant.

**Очередь задач (опционально):**
- Celery: задача `create_bot_container(bot_id)` → оркестратор создаёт контейнер.
- При ошибке — retry, уведомление, статус бота = `error`.

**Мониторинг контейнеров:**
- Healthcheck: периодический запрос к процессу внутри контейнера.
- При падении — перезапуск (restart policy) или алерт.

### 1.4 Детализация: обработка Telegram updates внутри контейнера

**Вариант A: Long polling**
- Внутри контейнера: цикл `getUpdates` с `offset`.
- Плюсы: не нужен публичный URL, проще для разработки.
- Минусы: задержка, один процесс на бота.

**Вариант B: Webhook**
- Единый ingress (nginx/traefik) маршрутизирует по path `/webhook/{bot_token_hash}` к нужному контейнеру.
- Контейнер слушает HTTP; при получении update — обработка.
- Плюсы: масштабируемость, низкая задержка.
- Минусы: нужен HTTPS, настройка маршрутизации.

**Поток обработки сообщения (внутри контейнера):**
1. Получить update (polling или webhook).
2. Извлечь `message.text`, `chat_id`.
3. Загрузить config бота из БД/файла (system_prompt, model).
4. Вызвать LangGraph-агента: `retrieve` (RAG) → `generate` (LLM) → ответ.
5. Отправить ответ через `sendMessage`.
6. Записать метрики (токены, latency) в централизованное хранилище.

## 2. База знаний и RAG

**Цель:** пользователь (через диалог с агентом) загружает документ в бота; клиентский бот отвечает с опорой на базу знаний. RAG — Qdrant.

### 2.1 Элементы

| # | Элемент | Описание | Зависимости |
|---|---------|----------|-------------|
| 2.1.1 | **Хранение документов** | Агент запрашивает файл в диалоге (прототип: один документ на бота); сохранение в storage (S3/локаль); метаданные в БД; привязка к container_id/bot_id | 1.1.2 |
| 2.1.2 | **Чанкинг и эмбеддинги** | Разбиение документа на чанки; вызов embedding-модели; сохранение векторов в Qdrant (отдельная collection на бота для изоляции) | 2.1.1 |
| 2.1.3 | **RAG-поиск** | По запросу конечного пользователя: эмбеддинг запроса → поиск top-k в Qdrant → формирование контекста для LLM | 2.1.2 |
| 2.1.4 | **Интеграция в LangGraph-агента бота** | В графе клиентского агента: нода RAG → подстановка контекста в промпт → вызов LLM | 1.1.5, 3.x |

### 2.2 Порядок реализации

1. Загрузка и хранение одного документа (2.1.1).  
2. Чанкинг + эмбеддинги + векторное хранилище (2.1.2).  
3. RAG-поиск (2.1.3).  
4. Подключение RAG к агенту (2.1.4).

### 2.3 Детализация: RAG-пайплайн (Qdrant)

**Структура Qdrant:**
- Одна collection на бота: `bot_{bot_id}` (или namespace в одной collection).
- Размерность векторов — по embedding-модели (например, 384 или 1536).
- Payload: `text`, `metadata` (source, chunk_id).

**Чанкинг:**
- Стратегия: RecursiveCharacterTextSplitter (LangChain) или аналогичная.
- Параметры: chunk_size=500–1000, overlap=100–200.
- Поддержка форматов: TXT, PDF (PyPDF2/pdfplumber), DOCX (python-docx).

**Эмбеддинги:**
- Модель: совместимая с GigaChat/Yandex (или отдельная embedding-модель, напр. sentence-transformers).
- Batch-загрузка при индексации для экономии вызовов.

**RAG-поиск в рантайме:**
1. Эмбеддинг запроса пользователя.
2. `Qdrant.search(collection=bot_{bot_id}, query_vector, limit=5)`.
3. Конкатенация `text` найденных чанков в контекст.
4. Подстановка в промпт: `context: {chunks}\n\nquestion: {user_message}`.

### 2.4 Детализация: LangGraph клиентского RAG-агента

| Нода | Назначение |
|------|------------|
| `retrieve` | RAG-поиск в Qdrant (collection бота); возврат контекста |
| `generate` | Формирование промпта (system + context + history + question); вызов LLM (GigaChat/YandexGPT) |
| `respond` | Возврат ответа пользователю |

**Граф:** `retrieve` → `generate` → `respond` → END. (Линейный граф для прототипа; при необходимости — ветвление, например, для уточняющих вопросов.)

**Конфиг внутри контейнера:** читается при старте или при каждом запросе (system_prompt, model_id, temperature).

### 4.3 Детализация: сбор метрик и учёт стоимости LLM

**События для записи (на каждый вызов LLM):**
| Поле | Тип | Описание |
|------|-----|----------|
| bot_id | uuid | Идентификатор бота |
| tenant_id | uuid | Владелец |
| request_id | str | Идемпотентность, связь с трейсом |
| model | str | GigaChat, YandexGPT и т.д. |
| input_tokens | int | Токены запроса |
| output_tokens | int | Токены ответа |
| cost | decimal | Стоимость (по тарифу провайдера) |
| latency_ms | int | Время ответа LLM |
| timestamp | datetime | Время события |
| error | str? | Текст ошибки при сбое |

**Тарифы по провайдерам (конфиг):**
- GigaChat: цена за 1K токенов (input/output могут отличаться).
- YandexGPT: аналогично.
- Расчёт: `cost = (input_tokens/1000 * price_in) + (output_tokens/1000 * price_out)`.

**Хранение:** PostgreSQL (таблица `llm_usage`) или специализированная БД (TimescaleDB для временных рядов). Опционально — отправка в очередь, асинхронная запись.

### 5.3 Детализация: трейсы и логи

**Структура трейса (LangGraph):**
- Каждый вызов клиентского агента — один trace_id.
- Шаги: `retrieve` (input: query, output: chunks_count), `generate` (input: prompt_preview, output: response_preview, tokens, latency).
- Сохранение: LangSmith/LangFuse или кастомная таблица `agent_traces` (trace_id, bot_id, steps_json, created_at).

**Логи:**
- Уровни: DEBUG, INFO, WARNING, ERROR.
- Обязательные поля: timestamp, level, bot_id, container_id, request_id, message.
- Сбор: stdout контейнеров → централизованный сборщик (Loki, ELK) или запись в PostgreSQL.

**Доступ из контейнера:** контейнер отправляет метрики/логи через HTTP в оркестратор или пишет в общую очередь (Redis stream, Kafka).

2. Проверка доступа во всех точках входа (6.1.2).  
3. Позже: оплата (6.1.4).

### 6.3 Детализация: регистрация и проверка доступа

**Первый контакт пользователя:**
1. Пользователь пишет боту продукта в Telegram.
2. По `telegram_user_id` проверяем наличие tenant.
3. Если нет — агент приветствует и предлагает начать trial; при согласии вызывается `create_tenant_and_trial`.
4. Сессия привязывается к tenant_id.

**Проверка доступа (при каждом действии):**
- Если `trial_ends_at < now` и `subscription_plan != paid` → блокировка.
- Сообщение пользователю: «Пробный период закончился. Оформите подписку для продолжения.»
- Исключение: чтение информации (список ботов, статус) может оставаться доступным.

**Точки проверки:**
- Перед вызовом любого tool (register_bot, upload_document и т.д.).
- Перед созданием контейнера.
- Опционально: middleware на уровне входящего сообщения.

## Идеи по развитию

1. **Изоляция контейнеров**  
   Один контейнер на бота; лимиты ресурсов (CPU, RAM) на контейнер; при хранении токенов — KMS/секреты; сеть: контейнеры не видят друг друга.

2. **Лимиты по тарифам**  
   Ограничения: кол-во ботов, размер базы знаний, запросов в месяц; проверка лимитов при действиях и при вызове агента.

3. **Несколько документов и типов файлов**  
   Расширить 2.1.1: несколько файлов на бота, поддержка PDF/DOCX; версионирование базы знаний.

4. **Сценарии и шаблоны**  
   Библиотека сценариев (поддержка, продажи, FAQ) с настраиваемыми промптами и шагами (3.1.3–3.1.4).

5. **Аналитика диалогов**  
   Агрегация: темы запросов, удовлетворённость (если есть оценки), конверсии — для отчёта и дашборда.

6. **Webhook vs long polling**  
   Для продакшена предпочтительнее webhook; нужен HTTPS и надёжная доставка updates.

7. **Rate limiting и защита**  
   Лимиты на запросы к боту и к API платформы; защита от злоупотреблений токенами и от DDoS.

8. **Уведомления**  
   Напоминания об окончании trial, о превышении лимитов, еженедельные/ежемесячные отчёты на email.

9. **Самообслуживание клиента**  
   Личный кабинет: управление ботами, загрузка документов, смена промпта, просмотр отчётов и дашборда.

10. **API для интеграций**  
    Публичное API для создания ботов, загрузки документов и управления конфигурацией (для партнёров и автоматизации).

## Краткая схема зависимостей

```
                    ┌─────────────────────────────────────────┐
                    │  Пользователь (естественный язык)       │
                    └─────────────────┬───────────────────────┘
                                      │
                                      ▼
[Tenant + Subscription] ──► [Агент-помощник (LangGraph)] ◄── Tools: регистрация,
                                      │                    загрузка, промпт, отчёт
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        │                             │                             │
        ▼                             ▼                             ▼
[Оркестратор контейнеров]    [Qdrant: collection/бот]    [Сбор метрик, трейсы]
        │                             │                             │
        ▼                             │                             ▼
[Контейнер бота 1] ◄──────────────────┘                    [Агрегация, отчёты]
[Контейнер бота 2] ...                                            │
  └─ LangGraph-агент + RAG + LLM (GigaChat/YandexGPT)              ▼
                                                          [Единый дашборд]
```

**Стек:** LangChain + LangGraph (агенты), Qdrant (RAG), GigaChat / YandexGPT (LLM).

Документ можно использовать как чек-лист: каждый элемент — отдельная подзадача при реализации.
